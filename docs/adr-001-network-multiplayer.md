## 1. 背景

- 專案目標從「單機 demo」擴為:**朋友從網站下載遊戲、彼此連線對戰**。
- 遊戲是回合制卡牌:低頻寬、事件驅動、不需要即時同步/預測回滾——聯機難度是所有類型裡最低的一檔。
- 發佈形式:網站提供下載的**桌面版**。本專案用 Forward+ 算繪(glow/SSAO),
  Godot 的 Web 匯出只支援 Compatibility 算繪器,故不考慮網頁版,不必為它降級畫面。

## 2. 決策

1. 用 **Godot 內建 high-level multiplayer + `ENetMultiplayerPeer`**,
   **host-client 模式**(開房的玩家 = 主機 = 規則權威),不做嚴格意義的 P2P。
2. **規則全部在 host 的 `BattleManager` 結算**:client 只送「意圖」
   (我想讓誰、用什麼技能、打誰),host 驗證(沿用 `*_block_reason` 那套)、
   結算、再把「結果」廣播給雙方播演出。
3. 抽牌等**亂數只在 host 發生**,把結果(抽到哪張卡的 id)廣播出去;
   不依賴「雙方同步亂數種子」這種脆弱做法。
4. 網路穿透:先支援**區網/虛擬區網**(ZeroTier、Radmin 之類)與手動 port forward;
   公開配對、NAT 穿透(noray relay 或 WebRTC)留到真的需要時再加(YAGNI)。

## 3. 理由

- **現有架構天生適合**:「演出/規則分離」+ 所有行動都收斂在
  `action_performed(caster, skill, target)` 一條信號 + `BattleManager` 是唯一規則權威
  ——行動本來就是「一則可序列化的訊息」,聯機只是把這則訊息改成走網路。
- ENet 是引擎內建、文件與範例最多、程式碼量最少的路;回合制不在乎它的延遲特性。
- 真 P2P(WebRTC)需要訊令伺服器+TURN 備援;Steam P2P 綁 Steam 發行。
  對「給朋友玩」的規模都是過度工程。

## 4. 取捨(想過而接受的)

- **host 是權威 = host 理論上可作弊**:朋友間對戰,host 驗證(現成的
  block_reason 機制)已足夠;不做伺服器仲裁。
- **穿透要自己想辦法**(虛擬區網/port forward):朋友間可接受;
  若未來公開發行,再補 relay——屆時只換「連線建立」那層,權威模型不動。
- **host 斷線 = 這局結束**:不做主機遷移。回合制一局 10~20 分鐘,重開成本低。

## 5. 後果(動工時的改動清單)

- `BattleManager`:魔力池拆成雙方各一份;加「回合歸屬」(現在輪到誰);
  行動驗證多一條「不是你的回合/不是你的單位就擋下」。
- `CardManager`:移除「可以指揮敵方單位」的沙盒行為(當初就是為了自測留的)。
- 新增**大廳場景**:開房(host)/ 輸 IP 加入(join);主選單加「連線對戰」入口。
- `PlayerHand`:對手手牌只同步**張數**(卡背),內容留在 host。
- 發佈:Windows 匯出 preset(icon、版本號)+ itch.io 或 GitHub Releases 下載頁
  (自架網站對「給朋友下載」是過度工程,靜態頁+現成託管就夠)。
